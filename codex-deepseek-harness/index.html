Codex 与 DeepSeek
Harness 的分岔

它们解决的是同一类问题：让模型在长任务里调用工具、管理上下文、执行代码并可被产品界面控制。但两者的第一性目标不同——一个优先把编程 Agent 做成稳定产品内核，另一个优先把 Agent Runtime 做成可替换的插件框架。

研究日期 2026‑08‑22 Codex commit 51ebf5b DeepSeek Harness commit b150a55 仅采用官方仓库 / 官方文章 源码级静态拆解，未做性能压测 完整视图：14 张关系图 / 28 条证据

【合理推断】 一句话结论

Codex 是“产品化 Harness”：固定 Rust Core、Responses API 中心、App Server 稳定外壳；DeepSeek Harness 是“框架化 Harness”：Cordis 插件树、事件溯源会话、能力接缝可替换。不是谁绝对更先进，而是谁更贴近你的系统目标。

选 Codex，如果你要

尽快落地可靠的 Coding Agent 产品，并让 CLI、IDE、桌面端共享一致的 Thread / Turn / Item、审批与沙箱语义。

选 DeepSeek Harness，如果你要

搭建 Agent 平台或研究 Runtime，需要替换模型适配器、工具、日志、文件系统、子进程、执行环境甚至 Agent Loop。

01 / Scope

先把比较边界钉死

本报告拆的是 Harness / Agent Runtime，不是 GPT 与 DeepSeek 模型能力对比，也不把公开接口无法证明的内部实现当事实。

比较对象

【已确认】 Codex 开源仓库中的 codex-rs/core、App Server、工具路由、rollout、模型 Provider 与多 Agent 控制。

【已确认】 DeepSeek Harness 的 Cordis 容器、agent-loop、session、tools、sandbox、subagent、API gateway 与官方 profiles。

不比较什么

【未知】 两者在同一模型、同一任务、同一硬件上的完成率、吞吐、Token 成本和端到端延迟；当前没有执行公平压测。

【未知】 闭源线上服务是否还有未公开的调度、安全或记忆层。

证据等级

【已确认】 直接来自源码、仓库文档或官方文章。

【合理推断】 由多个已确认结构归纳出的设计取向。

【建议设计】 本报告提出的 To‑Be。

本次启用的三个品类扩展

【已确认】 助手 / Copilot：上下文、建议与执行边界、确认门、中断和恢复；编程 / 开发者 AI：仓库、补丁、命令、测试、权限与供应链风险；Agent 平台 / 自动化：Loop、工具调度、状态机、幂等、补偿、可观测与多 Agent。未启用 AIGC、医疗、客服或推荐系统专用框架。

02 / Design DNA

同一道题，两种架构基因

最关键的差异并不在“都有工具调用”，而在什么被固定、什么被开放，以及系统真相存放在哪里。

【已确认】
Core first

Codex：固定内核，稳定外协议

公开说明把 Codex Core 定义为每条线程的 library + runtime，App Server 再把它暴露成双向 JSON‑RPC。模型请求以 Responses API 语义为中心，Thread / Turn / Item 是产品状态主轴。

  • 重点：产品一致性、生命周期、审批、沙箱、事件推送
  • 外部扩展：工具、MCP、Skills、配置、客户端、模型 Provider
  • 系统真相：会话历史 + rollout 持久化 + ThreadManager 活跃状态

【已确认】
Plugin first

DeepSeek：一切插件，事件为轴

官方架构明确声明 Cordis 容器、模型适配器、工具注册表、会话日志、Agent Loop 都可替换；profile / bundle 只是可装载的一组默认选择，而非特权核心。

  • 重点：可替换性、组合性、运行时接缝、事件可重放

03 / Product

先看它们分别服务谁

同样叫 Harness，Codex 把价值交付到“完成一个编码任务”，DeepSeek Harness 把价值交付到“组合出一个可控 Runtime”。这是后续所有技术差异的来源。

原替代方案

Codex 用户原本手动读仓库、编辑、跑命令和串联工具；DeepSeek 用户原本维护自研 loop、provider SDK、工具协议与持久化层。

AI 的角色

【合理推断】 两者都覆盖理解、规划、生成与执行，但 Codex 把“产品任务推进”作为主轴，DeepSeek 把“运行时编排”作为主轴。

失败代价

前者主要是错误修改、越权执行或任务未完成；后者还包含插件组合不兼容、事件投影错误与自定义后端行为漂移。

04 / Journey

端到端用户旅程不是同一条

下图同时分开“用户看到什么”和“系统真正完成什么”，并保留权限拒绝、工具失败、上下文压缩和中断恢复分支。

05 / Capabilities

功能域与 AI 能力地图

这里启用三个品类扩展：助手/Copilot、编程/开发者 AI、Agent 平台/自动化。没有证据支持的内建 RAG、长期记忆和动态模型路由继续保持未知。

06 / As-Is

两套公开 As‑Is 架构

这是公开源码中可确认的组件关系；没有把“可能存在”的线上服务补进图里。

【合理推断】 控制权的分配不同

Codex 把较多产品语义压进统一内核，因此客户端更薄、行为更一致；DeepSeek 把更多语义暴露为插件接缝，因此平台定制更自由，但集成方也要承担更多组合测试、依赖顺序与兼容性责任。

07 / Agent Loop

一次任务到底怎样跑

两边都不是“模型一次回答完”，而是多 Step 循环：组装上下文 → 模型流式输出 → 识别工具 → 执行 → 回灌 → 继续，直到助手消息结束或被中断。

08 / Mechanisms

真正拉开差距的八个机制

这里不看命名热闹，专看替换边界、恢复边界和安全边界。

机制CodexDeepSeek Harness架构含义
外部控制协议【已确认】 App Server 是稳定产品边界；双向 JSON‑RPC，统一 Thread / Turn / Item 与事件。【已确认】 Web profile 有双边 Typed RPC；远端只做 unary，事件流单独传输。Codex 更产品化：跨客户端接入契约更集中。DeepSeek 的 Host/Client gateway 更像可组合 profile 组件。
Agent Loop 可替换性【合理推断】 公开默认路线是复用固定 Core；没有看到与 DeepSeek AgentFactory 对等的 loop 插件契约。【已确认】 Agent Loop、模型适配器、工具注册表、会话日志都明确可替换。DeepSeek 更框架化，适合运行时实验；Codex 减少组合爆炸。
上下文与真相源【已确认】 Conversation history 供采样；rollout JSONL 选择性记录可重放项目，瞬态事件不全部持久化。【已确认】 append‑only Event Log 是模型上下文真相源；model-visible 内容必须可由日志重建。DeepSeek 的审计 / 重放不变量更硬；Codex 将产品状态与持久化策略区分得更细。
模型抽象【已确认】 Provider 可配置 OpenAI、Bedrock、Ollama、LM Studio 等，但 wire contract 当前只有 Responses API。【已确认】 Provider / ModelAdapter 把多种供应商输出归一成 StreamChunk；请求头记录精确 adapter / model 元数据。DeepSeek 更协议中立；Codex 对 Responses 语义整合更深。
工具执行【已确认】 ToolRouter + Registry 解析 function/custom/tool search；模型可声明 parallel tool calls，运行期维护 tool futures。【已确认】 native / code / both；有 bounded pool、exclusive barrier、模型顺序提交和 guarded pipeline。两者都支持并发；DeepSeek 对调度规则和 Code Mode 的公开契约更细。
沙箱 / 权限【已确认】 Turn 级 approval、sandbox、permission profile；权限请求覆盖文件系统与网络，支持 user / auto review。【已确认】 Sandbox 明确只管文件系统；Linux bwrap/Landlock、macOS Seatbelt、Windows ACL；审批和 preset 独立组合并 fail‑closed。Codex 权限面更贴近完整产品策略；DeepSeek 模块边界更清楚，但网络 / 进程限制需另组能力。
压缩 / 恢复【已确认】 Token 超阈值可自动 compaction；摘要和 world state 替换历史，Responses endpoint 还可执行服务端压缩。【已确认】 Compactor 是可选接缝；start / summary / end 进入事件日志，异常恢复可追加 interrupted turn。Codex 优先无感持续运行；DeepSeek 优先把压缩与恢复做成可观察事件。

09 / Model & Context

模型只是运行链中的一层

两边都把模型请求包在上下文、工具和状态系统之间；真正的分歧是模型协议如何抽象、哪些状态必须可重建。

10 / Safety

工具能跑不等于应该跑

编程 Agent 的核心风险来自文件、命令、网络、凭据和外部副作用。两边都做审批与隔离，但责任分层方式不同。

11 / Multi-Agent

两者都有多 Agent，但控制模型不同

不要把“存在子 Agent”误写成“所有任务都必须多 Agent”。默认单 Agent loop 仍是地基；子 Agent 只在可分解任务、上下文隔离或专门执行后端有价值。

12 / Ten layers

十层产品架构对照

把代码模块翻译成产品经理可用于选型、PRD 和技术评审的分层语言。

13 / Evaluation

完成、评测与运营不能混为一谈

源码能证明两边都有事件、usage、rollout 或重放能力，但不能证明它们已经具备同一套线上评测、企业 SLA 或商业运营体系。

14 / Decision

选型不要问“谁更强”

问你的核心风险是产品不一致，还是框架不可替换。

更适合 Codex 的项目

【合理推断】
  • 核心产品就是 coding agent / developer copilot
  • CLI、IDE、桌面端要共享一致会话与审批语义
  • 团队希望减少 Runtime 组合决策，优先稳定迭代
  • 愿意围绕 Responses API 及其事件语义深度集成
  • 多 Agent 是产品功能，而非任意后端联邦层

代价：loop、状态投影和模型协议的替换自由度较低。

更适合 DeepSeek Harness 的项目

【合理推断】
  • 核心产品是 Agent 平台 / Runtime / 研究基础设施
  • 必须同时接多模型协议、多文件系统或远程执行环境
  • 要实验不同 loop、compaction、subagent provider
  • 审计、重放和请求重建是硬性工程约束
  • 团队能承担插件依赖、版本兼容和组合测试成本

代价：developer preview 阶段，产品协议和默认体验需要自行收敛。

不要用当前证据做的决定

【未知】 不能据此声称 DeepSeek 更快、更省 Token，或 Codex 任务完成率更高；也不能把仓库活跃度直接等同于生产稳定性。若要技术选型，下一步应在同一模型、同一工具和同一任务集上跑等价基准。

15 / To-Be

最值得借鉴的是混合，而非站队

如果从零搭企业级 Agent 平台，可以把 Codex 的产品外壳与 DeepSeek 的内部接缝纪律组合起来。

控制面

稳定对象：Thread、Turn、Item、Approval、Permission Request。

稳定协议：双向 RPC + 版本协商 + 服务端事件。

数据面

唯一真相：不可变 Event Log。

派生状态：模型消息、UI 时间线、审计视图、恢复点全部由 projection 生成。

能力面

统一接缝：ModelAdapter、ToolExecutor、ExecutionWorld、Compactor、SubagentProvider。

策略：权限与执行分离，但以一个产品 preset 对外呈现。

最小落地顺序

【建议设计】 先定事件模型与外部生命周期 → 再定模型/工具接缝 → 再做沙箱和审批 → 最后扩展多 Agent。不要先做 team DAG；单 Agent 的可恢复、可审计闭环才是地基。

16 / Risks

关键风险与待验证项

这些问题会直接改变技术选型，但公开静态源码不能给出答案。

Codex 待验证

  • 【未知】 非 OpenAI 模型经 Responses 兼容层时，流事件、工具调用、压缩语义能否无损。
  • 【未知】 大规模并发 Thread 下的内存占用、rollout IO 和 App Server backpressure。
  • 【未知】 开源 Core 与线上 Codex 产品的功能差集。

DeepSeek 待验证

  • 【未知】 plugin 组合在长时间运行下的卸载、异常隔离与版本兼容成本。
  • 【未知】 developer preview 到稳定协议前，profile/API 的破坏性变更频率。
  • 【未知】 文件沙箱以外的网络、进程、密钥访问如何形成统一企业策略。
